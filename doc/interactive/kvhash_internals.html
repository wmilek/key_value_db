kvhash internals

A live model of how kvhash lays a map out on flash. Pick a population and watch the geometry it derives, add entries and see where each one lands, and lower the spill thresholds to detach keys and values into blobs of their own. Every operation runs a port of the kvhash.c code path against an in-browser blob store and lists each flash read, write and delete it makes.

      Modelled from lib/containers/kvhash/kvhash.c, doc/impl/l2_kvhash.md and doc/proposals/2026-10-09-kvhash-spill.md. The port follows derive_geometry, resolve_leaf, bkt_entry, bkt_find, kvhash_get/set/del/destroy step for step, with the same CRC-32 (bucket hash) and CRC-32C (key fingerprint), little-endian. blob_db itself is reduced to an id → bytes map: slots, compaction, segments and timing are not modelled, and next/count are computed by walking the model rather than traced.

      The example entries loaded on open are sample data, written with the policy set to 24 / 40 so some of them spill.
