# Design proposal — the Set shape, and a `kvhash` set provider

Status: **proposal** · 2026-10-31
· Target contract: new `include/app/lib/containers/shape_set.h`; adds a third
  shape to `doc/layers/l2_containers.md` §3
· Target implementation: `lib/containers/kvhash/` (split, see §5), plus a
  generic adapter `lib/containers/set_over_map/`
· Builds on: `doc/impl/l2_kvhash.md`, `doc/proposals/2026-10-09-kvhash-spill.md`
· Governed by `doc/principles.md`

**The ask.** Besides Map, the stack wants a **Set**: a collection of keys
with no values, answering membership. Embedded constraints mean the
implementation should reuse as much of `kvhash` as possible: the directory
format, geometry derivation, crash ordering, `next`, `count`, `destroy` and
test hooks are all proven, and a second copy of them would cost flash and
review effort. But it should still keep what a set can do better than a map
whose values are empty.

**Short answer.** Three pieces, delivered in this order:

1. **`shape_set.h`**: the contract, `create · stat · has · add · del · next ·
   count · destroy`. `add` on a key that is already present writes nothing
   and returns `-EEXIST`.
2. **`set_over_map`**: a ~150-line adapter that turns *any* `map_ops` into
   `set_ops`. It gets the semantics right (no write on re-add, exact
   `-EEXIST`/`-ENOENT`) but not the density. It is also the reference the
   native provider is tested against.
3. **`kvhash_set_ops`**: kvhash with one thing swapped, the **bucket record
   codec**. Everything above the bucket (directories, levels, geometry,
   `next` order, `count`, `destroy`, power-cut hooks) is shared code. A set
   record has no value field, and its key header is **1 byte** for keys up to
   127 B, against 4 bytes in a map. That fits 1.2–1.6× as many members in a
   bucket for the key sizes embedded sets use (§4.2). A new member reads its
   path once, and a re-add writes nothing.

---

## 1. What a set can do better than `map<key, "">`

Each point below is a property the native provider keeps. The adapter keeps
only the ones marked *semantic*.

| # | Advantage | Kind | Where it comes from |
|---|---|---|---|
| A1 | `add` of a present key **writes nothing**. A map `set` always rewrites the bucket, even when the value is unchanged. | semantic | no value can differ |
| A2 | `add`/`del` **report insert vs. no-op** (`-EEXIST` / `-ENOENT`), so a caller can keep an exact count with no probe. `shape_map.h` `count` asks map callers to probe with `get` first. | semantic | contract |
| A3 | **Denser buckets**: no `vlen` field and a 1-byte key header. That means more headroom before `-ENOSPC` on one level, and fewer buckets (smaller directories, less write traffic per add) on two. | format | record codec (§4) |
| A4 | **One pass per add**. The adapter has to probe (`get`) and then `set`, reading the path twice. The native `add` reads it once. | cost | native op |
| A5 | **Smaller code** in a set-only build: no value spill, no `ent_value`, no out-buffer / `-ENOMEM` protocol for values. | footprint | file split (§5) |

Considered and **not** proposed as advantages:

- **Sorted buckets.** A bucket sorted in `next` order would let `has` stop
  early and `next` stop at the first larger key. That saves CPU only. The
  bucket is already in RAM when it is scanned, and the flash reads are the
  same. It would also fork `bkt_find`/`bkt_first_after`, the code this
  design exists to share.
- **Fixed-width keys** (`key_len` declared at create, records with no
  header). That saves one byte more than A3 and needs a width stored in the
  directory. The 8-byte directory header has no free byte, and widening it
  changes `DIR_HDR_LEN`/`MAX_BUCKETS` throughout the core. It is left for a
  later version byte if a workload asks for it.
- **Lossy (fingerprint-only) membership.** It is a different contract (false
  positives, keys cannot be enumerated). If it is wanted, it should be its
  own shape.

## 2. The contract: `shape_set.h`

The shape mirrors `shape_map.h` deliberately. A caller who knows one knows
the other, and the conformance suite can share its scaffolding.

```c
struct set_config {            /* same rules as map_config: 0 = unknown, set = binding */
	size_t expected_members;
	size_t typical_key_bytes;
	size_t max_key_bytes;
};

struct set_info {              /* same meaning as map_info */
	uint8_t  depth;
	uint16_t fanout;
	uint32_t buckets;
	size_t   key_bytes_limit;
};

struct set_ops {
	int (*create)(uint64_t root, const struct set_config *cfg);
	int (*stat)(uint64_t root, struct set_info *out);

	/* 0 present · -ENOENT absent · -EINVAL bad key */
	int (*has)(uint64_t root, const void *key, size_t klen);

	/* 0 added · -EEXIST already present, NOTHING WRITTEN · -ENOSPC · -EINVAL · -EIO */
	int (*add)(uint64_t root, const void *key, size_t klen);

	/* 0 removed · -ENOENT absent · -EINVAL */
	int (*del)(uint64_t root, const void *key, size_t klen);

	/* stateless enumeration, exactly map_ops.next without the value buffers */
	int (*next)(uint64_t root, const void *key, size_t klen,
		    void *kout, size_t kout_sz, size_t *kout_len);

	int (*count)(uint64_t root, size_t *out);   /* as map_ops.count */
	int (*destroy)(uint64_t root);              /* as map_ops.destroy, §2.4 */
};
```

Key rules, enumeration order, the `next`-is-stateless guarantees, `count`
exactness, and the `destroy` contract are **copied verbatim** from
`shape_map.h` with "entry" replaced by "member". Nothing new is invented
there.

**Why `-EEXIST` and not `0` for a repeated add.** Both are defensible: the
set ends up in the requested state either way. `-EEXIST` wins on three
counts:

- It carries the one bit (A2) the caller otherwise has to buy with a probe.
- It matches `rootreg`, which already answers `-EEXIST` on a duplicate.
- It keeps the shape's "`0` or negative" rule. A positive "already there"
  return would repeat the near-full warning that `l2_kvhash.md` §6.3
  removed: 45 call sites reading `rc != 0` as failure.

A caller that does not care writes `if (rc != 0 && rc != -EEXIST)`.

## 3. The generic adapter: `set_over_map`

```c
int set_over_map_bind(struct set_over_map *s, const struct map_ops *m);
extern const struct set_ops set_over_map_ops;   /* for a compile-time bound map */
```

| Set op | Implemented as | Reads / writes at depth *d* |
|---|---|---|
| `has` | `get(out_sz = 0)`: 0 or `-ENOMEM` means present | *d*+1 / 0 |
| `add` | `has`, then `-EEXIST`, or `set(key, NULL, 0)` | 2(*d*+1) / 1 on insert; *d*+1 / 0 on re-add |
| `del`, `count`, `destroy`, `create`, `stat` | forwarded (config/info fields renamed) | as the map |
| `next` | `map.next` with `vout_sz = 0` (the value is always empty) | as the map |

It is a few hundred bytes. It gives A1 and A2 to every Map provider (kvhash
now, kvlist and kvtree when they land, and kvtree brings ordered sets for
free). Its costs are the double path read on insert (it lacks A4) and the
map's record size (it lacks A3). It is the right backend for small or rarely
written sets. It is also the **oracle** for §6: the native provider must be
indistinguishable from it.

## 4. The native provider: kvhash with a different record codec

### 4.1 What is shared, and the one seam

Today every bucket access in `kvhash.c` goes through exactly two places:

- **`bkt_entry()`**: "the one parser of a packed bucket". `bkt_find`,
  `bkt_first_after`/`okey`, `bkt_entries` (count) and `release_bucket`
  (destroy) all consume its `struct ent` and never touch raw bytes.
- **The entry writer in `kvhash_set()`**: the `put_u16`/`memcpy` block that
  appends an entry.

That is the seam. A set record parses into the **same `struct ent`** with
`vl = 0`, `vspill = false`, and `vpos` at the end of the key. Every consumer
then works unchanged, including `release_bucket`, which releases a spilled
key blob and skips the absent value. Concretely:

| Shared, unchanged | Set-specific (new) | Map-specific (moves out) |
|---|---|---|
| directory format, `dir_*`, `resolve_leaf`, `sub_load`, `top_child` | record parse branch in `bkt_entry` (~25 lines) | `ent_value`, value spill, same-length value fast path |
| `derive_geometry`, `fill_info`, `create` (2-level build) | `kvhset_has` / `_add` / `_del` (~150 lines) | `kvhash_get` / `_set` / `_del` |
| `struct ent`, `bkt_find`, key spill (`key_src`, `key_chunk`, `key_cmp_bytes`), `release_part` | set record writer (~20 lines) | value copy-out in `next` |
| `okey` order, `bkt_first_after`, `leaf_/tree_first_after`, `count`, `destroy`, `release_bucket(s)` | `set_ops` vector, `set_config` → geometry translation | `map_ops` vector |
| `kv_update`/`kv_delete` power-cut hooks, `FP_MASK`, `key_hash`/`hash_fp`, `dir_buf`/`bkt_buf` | | |

The only change to shared code is that the directory functions and
`bkt_entry` take a **kind** (below) instead of hard-coded constants.

### 4.2 On-flash format

**Directory.** The layout is byte-for-byte the same as kvhash's. Only the
magics and the version series differ:

| Magic | Meaning |
|---|---|
| `'KVSE'` | a live set (root and, at depth 2, every sub-directory) |
| `'KVSD'` | `destroy` has committed on a set; buckets still being released |

The version byte starts at `1` for sets, independent of the map's `2..3`.
Distinct magics are what keep the typed-root invariant (§5.2 of
`l2_containers.md`). A map op pointed at a set root, or the reverse, fails
in `dir_load_raw` before any bucket could be parsed with the wrong codec.
Because sub-directories carry the magic too, `sub_load` checks the kind at
every level.

**Bucket record (set v1).** One leading byte decides the form. A key length
of 0 is never stored, so the byte `0x00` is free to mark a spilled key:

```
0x01..0x7f                     inline key, len = byte (1..127)          header 1 B
0x80|len_hi  len_lo            inline key, len = 15-bit (128..32767)    header 2 B
0x00  [u16 klen][u32 fp][u64 id]   spilled key (fp = CRC-32 bucket hash)  15 B total
```

The writer always uses the shortest form. A `0x80 0x00` header (length 0),
or a record that runs past `used`, ends the bucket exactly as a truncated
tail does today. The spill reference is the same 12 bytes as a map's
(`fp`, `id`), so `key_src` and `key_cmp_bytes` serve it unchanged. The spill
threshold is kvhash's existing `key_inline_max` write policy: one knob, read
only by the writer. A spilled set record is 15 B, so keys of 14 B or less
never gain from spilling.

**Density** (bytes per member; a map entry with an empty value costs
4 + key):

| Key | Example | `map<k,"">` | set | Bytes saved | Members per 256 B bucket (map → set) |
|---|---|---|---|---|---|
| 4 B | u32 id | 8 | 5 | 38 % (1.60×) | 32 → 51 |
| 6 B | BLE/MAC address | 10 | 7 | 30 % (1.43×) | 25 → 36 |
| 8 B | u64 id, card UID | 12 | 9 | 25 % (1.33×) | 21 → 28 |
| 16 B | UUID | 20 | 17 | 15 % (1.18×) | 12 → 15 |
| 32 B | SHA-256 | 36 | 33 | 8 % (1.09×) | 7 → 7 |

On one level this turns into headroom: `derive_geometry` targets 4 members
per bucket, so a denser bucket is further from `-ENOSPC` when the population
runs over its declaration. On two levels it turns into fewer buckets, because
the `MIN_BUCKET_BYTES` floor is computed from the declared bytes. In both
cases the bytes rewritten per `add` shrink by the same factor.

**Geometry.** `create` translates `set_config` into the core's derivation
with `typical = typical_key_bytes + 1` and `max = max_key_bytes + 2` (record
header included). The map's translation stays as it is today, so existing
maps derive identical geometries.

### 4.3 Operations and their cost

| Op | Native set (depth *d*) | `map<k,"">` via adapter |
|---|---|---|
| `has` | *d*+1 reads | *d*+1 reads |
| `add`, new | *d*+1 reads, 1 bucket write (+1 dir write if the bucket is fresh, +1 key blob if spilled) | 2(*d*+1) reads, same writes |
| `add`, present | *d*+1 reads, **0 writes** | *d*+1 reads, 0 writes |
| `del` | *d*+1 reads, 1 bucket write (+1 delete if spilled) | same |
| `next`, `count`, `destroy` | as kvhash | as kvhash |

`add` is `kvhash_set` with the value half removed: resolve the leaf, load
the bucket, `bkt_find`. On a hit it returns `-EEXIST` and stops. On a miss
it binds the spilled key blob if one is needed, appends the record, and
commits the bucket (the commit point). It publishes a fresh bucket into its
leaf directory last. `del` is `kvhash_del` minus the value release. There is
no overwrite path at all, so the "drop the old entry, re-append" compaction
and its undo leg disappear.

### 4.4 Crash safety

Nothing new is introduced. It is the argument `l2_kvhash.md` already makes:

- **`add` new / `del`**: one atomic bucket update is the commit. A fresh
  bucket is written before the directory names it, so a cut in between
  leaves an unreferenced blob, never a corrupt set. A spilled key blob is
  bound before the commit and released on the undo path, as in the map.
- **`add` present**: writes nothing, so there is nothing to analyse.
- **`destroy`**: stamp `'KVSD'`, release children bottom-up, delete the root
  last (§3 of `l2_kvhash.md`, unchanged code, kind-parametrised magic).
- **`count`** is exact after any cut, for the same reason as the map's.

The `kvhash_test_cut_after` / `kvhash_test_fp_mask` hooks live in the shared
core, so the existing crash-injection and collision tests apply to sets as
they are.

## 5. Code and Kconfig layout

```
lib/containers/kvhash/
  kvhash_internal.h   struct kvh_kind, core prototypes        (private)
  kvhash_core.c       everything in the "shared" column of §4.1
  kvhash_map.c        map_ops: get / set / del, value spill   ifdef KVHASH_MAP
  kvhash_set.c        set_ops: has / add / del                ifdef KVHASH_SET
lib/containers/set_over_map/
  set_over_map.c                                              ifdef SET_OVER_MAP
include/app/lib/containers/
  shape_set.h  kvhash.h (+ extern const struct set_ops kvhash_set_ops)
```

```c
struct kvh_kind {             /* one const instance per shape, in .rodata */
	uint32_t magic, dying;
	uint8_t  ver_min, ver_max, ver_create;
	bool     keyonly;         /* selects the record codec in bkt_entry */
};
```

`bkt_entry` branches on `IS_ENABLED(CONFIG_BLOB_CONTAINER_KVHASH_SET) &&
k->keyonly`. A map-only or set-only build compiles the other codec away, so
the seam costs no flash when unused (P4). The two scratch buffers stay in the
core and are shared by both shapes. They remain under the single-threaded
contract, so enabling both shapes adds **no RAM**.

```
config BLOB_CONTAINER_KVHASH            (existing symbol, unchanged meaning for current users)
if BLOB_CONTAINER_KVHASH
config BLOB_CONTAINER_KVHASH_MAP        bool "kvhash Map provider"   default y
config BLOB_CONTAINER_KVHASH_SET        bool "kvhash Set provider"
endif
config BLOB_CONTAINER_SET_OVER_MAP      bool "Set shape over any map_ops"
```

The core is a mechanical extraction from today's `kvhash.c` with no behaviour
change. It lands first, on its own, and the existing kvhash suite must pass
unmodified. That is how the split is shown to be pure reuse.

**Footprint expectation.** By line count, about 70 % of `kvhash.c` (~1 200 of
1 700 lines) is shape-independent core. `kvhash_set.c` should be about half
the size of `kvhash_map.c`. So a build with both shapes should cost about
15 % more flash than kvhash does now, and a set-only build should be smaller
than a map-only one. These are estimates. Acceptance is the `app_footprint`
measurement, before and after, on the nRF5340-DK.

## 6. Tests

Under `tests/lib/containers/`:

1. **Conformance suite** (`l2_containers.md` §8), run against each enabled
   `set_ops`: `set_over_map(kvhash_map_ops)` and `kvhash_set_ops`. Steps:
   empty set, add/has/del round-trips, binary and 1-byte keys, 127/128-byte
   keys (the header-form boundary), the `-EEXIST`/`-ENOENT` returns,
   persistence over remount, `next` completeness and stability under
   mutation, and `count`.
2. **Differential test**: the same random operation stream is applied to both
   providers. Every return code, `count`, and the full `next` walk (as a
   multiset) must match.
3. **No write on re-add**: `add` of a present key leaves blob_db's write
   counters (`blob_db_iostats`) unchanged.
4. **Crash injection** with `kvhash_test_cut_after` at every write of `add`
   (inline, spilled, fresh bucket), `del` and `destroy`. After each cut,
   remount: the set is complete-old or complete-new, `count` agrees with
   `has`, and a repeated `destroy` finishes.
5. **Typed root**: map ops on a set root, set ops on a map root, and a set
   op on a `'KVSD'` root (expect `-ENOENT`).
6. **Collisions**: `kvhash_test_fp_mask = 0` with spilled keys. `has`, `del`
   and `next` must still fall back to key bytes correctly.
7. **Density**: fill one bucket with 8-byte keys. The set holds ⌊payload/9⌋
   members where the adapter's map holds ⌊payload/12⌋.

## 7. Plan

| Step | Change | Risk |
|---|---|---|
| 1 | `shape_set.h` + `set_over_map` + conformance suite | none to existing code |
| 2 | Extract `kvhash_core.c` / `kvhash_map.c`; existing tests unmodified | refactor only; guarded by the current suite and the footprint check |
| 3 | `kvh_kind` threading; `kvhash_set.c`; differential and crash tests | new format, new magic; maps untouched on flash |
| 4 | `l2_containers.md` §3/§4 (three shapes; kvhash row gains "Set"), `l2_kvhash.md` §1 (set record) | docs |

Step 1 alone is useful and can ship independently. Steps 2–3 are where A3–A5
come from.

## 8. Open questions

- **Separate spill knob for sets?** This proposal shares `key_inline_max`.
  A product that holds a map of long keys and a set of long keys might want
  them to differ. The format allows it either way, because the threshold is
  write policy only.
- **Batch `next`** (several members per call from the bucket already in RAM)
  would cut a full walk from about *n*(*d*+1) reads to about
  buckets × (*d*+1). It would help Map just as much, so it belongs in a
  separate proposal covering both shapes.
- **Set algebra** (`union`/`intersect`/`diff`): with the same geometry, two
  sets' buckets line up index by index, so a one-pass bucket merge is
  possible. Nothing in this design blocks that, and nothing in it depends on
  it.
