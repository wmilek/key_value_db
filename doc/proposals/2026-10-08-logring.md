# Design change proposal — `logring`, a log container of per-entry i-nodes

Status: **accepted** · 2026-10-09 (proposed 2026-10-08)
· Target contract: `doc/layers/l2_containers.md` (§3 shapes, §4 containers, §5 invariants)
· Target implementation design: **replaces** `doc/impl/l2_logring.md` (the single-i-node sketch)
· Self-contained on L1 (no intent helper — eviction keeps its intent inline, §3.4)
· New dependency: Zephyr `sys_rand32_get()` — the non-crypto random subsystem (`select ENTROPY_GENERATOR`), not PSA (per-log epoch, §3.6)
· Supersedes: the single-i-node `logring` on branch `claude/log-container-type-0xl2dp` (PR #32), not yet on `main`
· Governed by `doc/principles.md`

**The ask.** Store a **large** device log — from a couple of MB up to **near
the whole flash partition** ("1–2 MB" is illustrative, *not* a ceiling) — as
many entries, **each its own i-node**, in a bounded ring: appends cheap and
kind to NOR, a forward drain with a **persistable, portable cursor**, the
ability to **reach the real end** without walking the whole log, and a cheap
way to **reject a stale cursor** (e.g. one left over from before a reformat).

**Short answer.** A **forward-linked chain of per-entry i-nodes with
pre-reserved ids**: each entry's `next_id` is an id already reserved via
`alloc_id()` but not yet bound, so an append simply *binds* that id — one new
blob written, nothing rewritten (~1× amplification, §2). A small **RAM handle**
caches the tail, so warm appends are O(1) and the root is written only at
**checkpoints** (~every K appends), leaving a persisted **waypoint** near the
end to `open`/`seek_newest` from. Reads use an **opaque cursor** that exports a
small **public moniker `{epoch, id}`** the caller serializes and protects
itself; the `epoch` is a per-log random tag that rejects a moniker from another
incarnation. Eviction is batched onto the checkpoint write with its intent held
**inline** in the root — no separate intent module.

---

## 1. Requirements

| # | Requirement | Consequence |
|---|---|---|
| R1 | A log may hold a **large** amount — up to **near the whole partition** (no fixed ceiling) | a chain of i-nodes; per-op cost must stay flat as the log grows |
| R2 | **Each entry is its own i-node** (its own stable id) | entries individually addressable/evictable; an entry id is the position |
| R3 | **Per-record durability** — each entry written straight to `blob_db` | every append is a flash commit; the only RAM is a rebuildable pointer cache |
| R4 | **Approximately** bounded ring, evict oldest over a **soft** budget | no crash-exact accumulator; the ring sits near, not exactly on, the budget |
| R5 | **Forward-only** reads (oldest → newest) | a singly-linked forward chain suffices |
| R6 | **Fast resume from a stored moniker** (O(1), not a scan) | the moniker names its entry; one read repositions |
| R7 | **Detect a moniker whose position was evicted** | retention gap is a reported outcome (`-ESTALE`) |
| R8 | Records are **caller-opaque bytes** | the container frames only a length |
| R9 | **Many independent logs coexist**, each a root id + handle | `create` yields a fresh root; logs share only the global id space |
| G1 | **Reach the real end** — read the newest / follow from the end | `seek_newest`, O(1) via the cached tail; no walk from `head` |
| **G2** | **Reject a stale moniker from a previous incarnation** (e.g. after a reformat, which reuses ids) | a per-log random **epoch** carried in the moniker and checked on use |

## 2. Why the obvious designs are too expensive

`blob_db` has **no append-to-blob primitive**: `blob_db_update(id, …)` replaces
the whole payload. Every "add one record" costs a whole blob write *somewhere*;
the question is whose.

| Design | How a record is added | Flash written per record | Note |
|---|---|---|---|
| **Packed segments** (N records per i-node) | rewrite the open segment blob | `S²/2R` to fill an `S`-byte segment with `R`-byte records → ~**32×** at `S`=4 KB, `R`=64 B | explodes for small records |
| **Chain, patch predecessor** (set old tail's `next_id`) | write new entry + rewrite old tail | ~**2×** | doubles wear |
| **Chain, pre-reserved id** *(accepted)* | **bind an already-reserved id the predecessor already points at** | ~**1×** (one new blob; nothing rewritten) | one i-node per entry |

## 3. Design

### 3.1 Objects and the handle

```
root  { magic 'CLOG', version, flags, capacity_bytes, epoch,      -- 1 i-node, rewritten
        waypoint_id, head_id(hint), live_bytes(hint),                only at checkpoints
        evict_from, evict_to }                                       (~1/K appends)
entry { next_id, len, bytes… }                                    -- 1 i-node PER record

logring_t (RAM handle, rebuilt at open):
      { root, epoch, capacity_bytes, tail_id, next_free,
        head_id, live_bytes, since_ckpt }
```

- `bytes` is caller-opaque (R8); `len` is `uint16` — an entry fits one
  `blob_db` payload (**no record spanning**, `-EMSGSIZE` above it).
- `next_id` points at a **reserved-but-unbound** id — the slot the next append
  binds.
- `epoch` is a per-log random tag (`sys_rand32_get()`) set at `create`; it
  guards monikers against a different incarnation of the log (G2).
- `waypoint_id` is a live entry *near* the end; the root carries no exact tail.
- `evict_from`/`evict_to` are the **inline eviction intent** (0 = none, §3.4).
- The **handle** caches the exact tail and the epoch; it holds no record data
  and is rebuilt by one bounded walk at `open` (§3.5). (`l2_containers.md` §2.3
  anticipates an L2 handle holding "the root id plus O(1) cursor state".)

### 3.2 The pre-reservation invariant

> `tail.next_id` is always an id `alloc_id()` returned that **no slot has been
> bound to yet**. The chain *ends* at the first `next_id` that `blob_db_get`
> reports `-ENOENT` because it is unbound.

`blob_db` keeps an allocated id durable and never re-issues it (as `rootreg`
relies on), so a reservation survives crashes at zero flash cost.

### 3.3 `append` — one write, warm O(1)

```
R  = h.next_free                         // cached; old_tail.next_id already == R
R2 = alloc_id()                          // reserve the next slot (durable, 0 flash)
write entry[R] = { next_id = R2, bytes } ◄── COMMIT: binding R makes it reachable
h.tail_id = R;  h.next_free = R2;  h.live_bytes += len;  h.since_ckpt++
if h.since_ckpt ≥ K  OR  h.live_bytes > capacity_bytes + slack:
        checkpoint(h)                    // §3.4 — the only root write
```

Binding `R` is the commit (the predecessor already points at it); nothing is
rewritten. Warm cost = **one entry write, zero reads**, ~1× amplification.

### 3.4 Checkpoint + batched eviction — the only root write, intent inline

Eviction must be **coupled to the checkpoint**: between checkpoints `head_id`
does not move, so the root's `head_id` stays a valid walk entry point and
`open` can trust it. R4's soft budget permits an overshoot of ~`slack`.

```
checkpoint(h):
  if h.live_bytes > capacity_bytes:
      walk head → new_head freeing ≥ (live_bytes − capacity_bytes)      // reads only
      evict_from = h.head_id;  evict_to = new_head;  h.head_id = new_head
  write root { waypoint = h.tail_id, head_id = h.head_id, live_bytes,
               evict_from, evict_to }                   ◄── single COMMIT (atomic)
  if evicting:
      delete the run [evict_from, evict_to) SUFFIX-FIRST (evict_from deleted last)
      // evict_from stays live until the end, so recovery can always re-enter
  h.since_ckpt = 0   // the inline intent is cleared by the NEXT checkpoint write
```

The one `root` write advances `head` **and** records the eviction run **and**
refreshes the waypoint, atomically. Deleting **suffix-first** keeps
`evict_from` live until the final delete, so a crash mid-cleanup leaves the
undeleted part a prefix still walkable from `evict_from`; `open` re-runs the
delete idempotently (§3.5). No per-step intent writes, no separate intent blob,
no intent module. The evicted entries form a chain segment whose id *values*
are not contiguous (other logs/users interleave allocations, R9), so cleanup
**follows the chain**, never "delete every id in a range." A hard `-ENOSPC` on
a bind forces an immediate checkpoint+evict regardless of the soft trigger.

### 3.5 `open` / recovery

`open(root, h)` reads the root and rebuilds the handle:

- **Finish any eviction.** If `evict_from != 0`, re-run the suffix-first delete
  of `[evict_from, evict_to)` (idempotent — `evict_from` was deleted last, so
  the remaining run is a prefix walkable from it). `head_id` is already
  `root.head_id` (advanced atomically with the intent).
- **Rebuild the tail.** Walk from `waypoint_id` via `next_id` to the first
  unbound id — the last bound entry is `tail_id`, the unbound id is
  `next_free`. Bounded by appends since the last checkpoint (< K).
- Adopt `epoch`, `capacity_bytes`, and the `head_id`/`live_bytes` hints.

The chain always ends at a reserved-unbound id, so the true end is found
regardless of crashes. (Waypoint-evicted — only if the live set shrank below
one checkpoint interval — falls back to a walk from `head_id`.)

### 3.6 Reading — opaque cursor, public moniker, epoch check

Reads follow the systemd-journal / `lseek` idiom: an opaque position, seek to
an end, step forward. The **portable** form is a public struct the caller
serializes itself.

```
logring_cursor — opaque, caller-allocated; holds { epoch, pos } internally
logring_moniker — PUBLIC struct the caller serializes: { uint32_t epoch; uint64_t id; }

seek_oldest(h, c)   → c = { epoch = h.epoch, pos = OLDEST }        (≈ seek_head)
seek_newest(h, c)   → c = { epoch = h.epoch, pos = h.tail_id }     (≈ seek_tail, O(1))
next(h, c, out…)    → deliver entry at c, advance c                (≈ sd_journal_next)
cursor_to_moniker(c, &m)   → m = { c.epoch, c.pos }    // export to serialize/transmit
cursor_from_moniker(c, &m) → c = { m.epoch, m.id }     // import a saved position
```

`next` first checks the cursor's epoch against the log's (`c.epoch != 0 &&
c.epoch != h.epoch → -ESTALE`), then delivers the entry at the cursor and
advances to its `next_id`. Detection:

- epoch mismatch (wrong incarnation, or a random/forged value) → **`-ESTALE`**.
- `pos < head_id`, or the entry reads `-ENOENT` while it should be live →
  **`-ESTALE`** (evicted; cursor resets to oldest). R7.
- the successor is the unbound frontier → **`-ENOENT`** caught up.

`seek_newest` reaches the real end in O(1) (G1); resume (R6) is one read.
`logring_moniker` has **public fields**: logring defines no wire format and
makes no durability/security guarantee for it — framing, versioning, and
integrity/secrecy are the **caller's** responsibility before it crosses a
trust boundary. The epoch rejects a stale/foreign/random moniker cheaply
(1/2³² accidental acceptance), but a *crafted* value carrying the live epoch
is stopped only by the caller's MAC — the epoch is **defense-in-depth**, not a
security control. This is the same "random-in-root" idea that can later seed
`kvhash`.

## 4. Cost summary (4 KB sectors)

| Op | Flash reads | Flash writes | Caller RAM |
|---|---|---|---|
| `create` | 0 | 1 (root) | O(1) |
| `open` | 1 (root) + walk (< K) [+ evict cleanup] | 0 | O(1) |
| `append` (warm) | 0 | 1 (entry) | len |
| `append` (checkpoint, evicting M) | walk M | 1 entry + 1 root + M deletes | len |
| `next` (steady) | 1–2 | 0 | entry len |
| `seek_newest` + `next` | 1 | 0 | entry len |
| `stats` | 0 (from handle) | 0 | O(1) |

Every row is **O(1) in the log's total size** and amplification is ~1×
regardless of size, so there is no capacity ceiling (R1). Top-end constraints
are allocator interactions: **compaction headroom** (size `capacity_bytes`
below the raw partition; `-ENOSPC` is the correctness floor) and, now ~1/K,
root-bucket wear.

## 5. Public API (`include/app/lib/containers/logring.h`)

```c
typedef struct logring logring_t;          /* opaque RAM handle (root + cached tail) */
typedef struct logring_cursor logring_cursor;   /* opaque live position (caller-allocated) */
struct logring_cfg     { uint32_t capacity_bytes; };            /* soft bound, non-zero */
struct logring_stats   { uint64_t oldest_id, newest_id; uint32_t count, bytes; };
struct logring_moniker { uint32_t epoch; uint64_t id; };        /* PUBLIC; caller serializes */

/* lifecycle */
int  logring_create (const struct logring_cfg *cfg, uint64_t *out_root);
int  logring_open   (uint64_t root, logring_t *h);
int  logring_destroy(logring_t *h);

/* write — durable on return; -EMSGSIZE if len > one payload */
int  logring_append (logring_t *h, const void *rec, size_t len, uint64_t *out_id);

/* read — forward-only, opaque cursor */
int  logring_seek_oldest(logring_t *h, logring_cursor *c);
int  logring_seek_newest(logring_t *h, logring_cursor *c);                   /* G1, O(1) */
int  logring_next   (logring_t *h, logring_cursor *c,
                     void *out, size_t out_sz, size_t *out_len, uint64_t *out_id);
     /* 0 · -ENOENT caught up · -ESTALE evicted/stale-epoch · -EMSGSIZE buf short */

/* portable moniker — public fields; caller owns framing/versioning/security */
void logring_cursor_to_moniker  (const logring_cursor *c, struct logring_moniker *out);
int  logring_cursor_from_moniker(logring_cursor *c, const struct logring_moniker *m);

/* introspection / maintenance */
int  logring_stats  (logring_t *h, struct logring_stats *out);  /* ids exact; count/bytes hints */
int  logring_reset  (logring_t *h);
```

`logring` keeps its own append/scan API (neither `map_ops` nor `seq_ops`;
`l2_containers.md` §3 allows it). Each `create` yields an independent
root/handle (R9); persist the root as any structure root (typically a
`rootreg` entry per log, `ROOTREG_KEY('CLOG', n)`).

## 6. Crash analysis (the P7 check)

**Append** — no intent; the only commit is binding the pre-reserved entry
(atomic `blob_db_update`). Complete-old or complete-new; a reserved-unbound id
costs zero flash; the RAM handle is rebuilt at `open`.

**Checkpoint/eviction** — the single root write (new `head` + waypoint + inline
`{evict_from, evict_to}`) is the commit, atomic. Before it: the run is still the
live head (no-op on recovery). After it: the run is detached and the inline
intent drives an idempotent, suffix-first re-delete at `open` (no leak, no
dangling, `evict_from` re-enterable). The intent is cleared by the next
checkpoint write.

## 7. Container-invariant checklist (`l2_containers.md` §5)

1. **Single-integer reachability** — the root id recovers the whole log (the
   handle is a rebuildable cache). ✓
2. **Typed root** — `'CLOG'` magic/version; wrong-type `open` → `-ENOTSUP`. ✓
3. **One commit point per mutation** — append = bind entry; eviction/checkpoint
   = the root write. ✓
4. **O(1) steady-state RAM** — the handle is a few integers; no per-entry RAM. ✓
5. **Bounded stack** — one payload buffer; the open walk is iterative, ≤ K. ✓

## 8. Kconfig

```
config BLOB_CONTAINER_LOGRING
	bool "logring — bounded per-entry log container"
	select ENTROPY_GENERATOR   # sys_rand32_get for the epoch (non-crypto, not PSA)

config BLOB_CONTAINER_LOGRING_CHECKPOINT   # K — appends between root checkpoints
	int  "logring checkpoint interval"
	default 32
```

No `select BLOB_CONTAINERS_INTENT` — eviction holds its intent inline (§3.4).
It `select`s `ENTROPY_GENERATOR` so the epoch's `sys_rand32_get()` resolves
from the non-crypto random subsystem on any backend, rather than relying on the
UBI backend's PSA stack to drag a generator in. `capacity_bytes` is a per-log
create-time parameter (soft hint). `K` trades open-walk length and eviction
overshoot (~K entries) against root-write frequency (~1/K); default 32.

## 10. Test plan (`tests/lib/containers/logring`, native_sim)

1. create → open → empty; `seek_oldest`/`seek_newest` + `next` → `-ENOENT`.
2. append/drain: ids increasing; oldest→newest; binary & zero-length; `seek_newest` delivers newest.
3. pre-reservation: `tail.next_id` unbound; next append binds exactly it.
4. **amplification guard**: bytes via flash shim — per-append ≈ entry size, root ≈ appends/K.
5. soft ring: append past `capacity_bytes`; eviction batches; `stats.bytes` within ~slack; `-ENOSPC` backstop evicts and the append still succeeds.
6. cursor resume: `to_moniker` → unmount/mount (`open` rebuilds) → `from_moniker` → `next` continues; O(1).
7. **epoch (G2)**: a moniker from a destroyed+recreated log (new epoch) → `next` → `-ESTALE`; a random moniker → `-ESTALE`.
8. **eviction detection (R7)**: hold a moniker, evict past it, `next` → `-ESTALE`.
9. **checkpoint/open**: crash with < K un-checkpointed appends; `open`'s walk recovers the exact tail.
10. **crash injection** (`blob_db_test_cut`) at each step of §3.3/§3.4: remount, assert complete-old/new, no unreferenced entry, inline intent re-run idempotent.
11. `destroy` removes all entries + root; `blob_db_count` returns to baseline.

## 11. Resolved decisions

- **D1 — capacity.** `capacity_bytes` per-log, **soft hint**; `-ENOSPC` hard backstop; no crash-exact accumulator. ✓
- **D2 — root-write wear.** Waypoint + RAM-cached tail + checkpoint every K; warm appends do no root write (~1/K). ✓
- **D3 — gap count on `-ESTALE`.** Detection only; no dense per-entry seq. ✓
- **D4 — per-entry tag.** None; rely on `blob_db`'s per-slot CRC. The moniker `epoch` (root-level) gives incarnation/forged-id detection; a per-entry epoch would additionally defend a *crafted-epoch* id pointing at a foreign blob, but that is the caller MAC's job — not added. ✓
- **D5 — eviction mechanism.** **Inline** intent in the root + suffix-first delete; **no** shared intent helper, `logring` is self-contained on L1. ✓
- **G1 — read the end.** `seek_newest`, O(1); forward-only. ✓
- **G2 — stale moniker.** Per-log random `epoch` (`sys_rand32_get`) in the root + moniker, checked by `next`; defense-in-depth alongside the caller's MAC. ✓

Remaining tunable, not blocking: **K** (default 32).

## 12. Summary

A large, individually-addressable log (up to near the whole partition, R1) is a
forward chain of per-entry i-nodes with **pre-reserved** links: each append
binds a durable, already-pointed-at id, writing one blob and rewriting nothing
(~1×). A **RAM handle** caches the tail so warm appends are O(1) and the root
is written only at **checkpoints** (~1/K), carrying the **waypoint**
(`open`/`seek_newest` anchor) and the **inline eviction intent** (batched,
suffix-first, re-enterable) — so `logring` is self-contained, no intent helper.
Reads use an **opaque cursor** exporting a **public `{epoch, id}` moniker** the
caller serializes and protects; `seek_newest` reaches the end in O(1) (G1), and
the per-log random `epoch` rejects a stale/foreign moniker (G2) as
defense-in-depth beside the caller's MAC. Every §5 invariant and P7 obligation
holds.
