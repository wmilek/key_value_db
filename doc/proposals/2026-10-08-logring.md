# Design change proposal — `logring`, a log container of per-entry i-nodes

Status: **accepted** · 2026-10-09 (proposed 2026-10-08)
· Target contract: `doc/layers/l2_containers.md` (§3 shapes, §4 containers, §5 invariants)
· Target implementation design: **replaces** `doc/impl/l2_logring.md` (the single-i-node sketch)
· Depends on: `lib/containers/intent` (scaffolded) — **eviction only**
· Supersedes: the single-i-node `logring` on branch `claude/log-container-type-0xl2dp` (PR #32), not yet on `main`
· Governed by `doc/principles.md`

**The ask.** Store a **large** device log — from a couple of MB up to **near
the whole flash partition** ("1–2 MB" is illustrative, *not* a ceiling) — as
many entries, **each its own i-node**, in a bounded ring: appends cheap and
kind to NOR, a forward drain with a **persistable cursor**, and the ability to
**reach the real end** (read the newest / follow new entries) without walking
the whole log.

**Short answer.** A **forward-linked chain of per-entry i-nodes with
pre-reserved ids**: each entry's `next_id` is an id already reserved via
`alloc_id()` but not yet bound, so an append simply *binds* that id — **one new
blob written, nothing rewritten** (~1× amplification, vs. 2× for a
patch-the-predecessor chain and up to 32× for packed segments, §2). A small
**RAM handle** caches the tail, so warm appends are O(1) and the root i-node is
written only at **checkpoints** (~every K appends), not every append — which
both dissolves the write hotspot and leaves a persisted **waypoint** near the
end to `open` from and to seek the end from. The cursor is an **opaque,
persistable position** (journal-/`lseek`-style); an aged-out position is
reported `-ESTALE`. Append needs no intent; only (batched) eviction carries a
small resumable run intent.

---

## 1. Requirements

| # | Requirement | Consequence |
|---|---|---|
| R1 | A log may hold a **large** amount — up to **near the whole partition** (no fixed ceiling) | a chain of i-nodes; per-op cost must stay flat as the log grows |
| R2 | **Each entry is its own i-node** (its own stable id) | entries are individually addressable/evictable; an entry id is the cursor |
| R3 | **Per-record durability** — each entry written straight to `blob_db` | every append is a flash commit; the only RAM is a rebuildable pointer cache |
| R4 | **Approximately** bounded ring, evict oldest over a **soft** budget | no crash-exact accumulator; the ring sits near, not exactly on, the budget |
| R5 | **Forward-only** reads (oldest → newest) | a singly-linked forward chain suffices |
| R6 | **Fast resume from a stored moniker** (O(1), not a scan) | the moniker names its entry; one read repositions |
| R7 | **Detect a moniker whose position was evicted** | retention gap is a reported outcome (`-ESTALE`) |
| R8 | Records are **caller-opaque bytes** | the container frames only a length |
| R9 | **Many independent logs coexist**, each a root id + handle | `create` yields a fresh root; logs share only the global id space |
| **G1** | **Reach the real end** — read the newest entry / follow from the end | `seek_newest`, O(1) via the cached tail; no walk from `head`, no per-append end write |

## 2. Why the obvious designs are too expensive

`blob_db` has **no append-to-blob primitive**: `blob_db_update(id, …)` replaces
the whole payload. Every "add one record" costs a whole blob write *somewhere*;
the question is whose.

| Design | How a record is added | Flash written per record | Note |
|---|---|---|---|
| **Packed segments** (N records per i-node) | rewrite the open segment blob | `S²/2R` to fill an `S`-byte segment with `R`-byte records → ~**32×** at `S`=4 KB, `R`=64 B | explodes for small records |
| **Chain, patch predecessor** (set old tail's `next_id`) | write new entry + rewrite old tail | ~**2×** (old tail's whole payload rewritten to flip 8 B) | constant, but doubles wear |
| **Chain, pre-reserved id** *(accepted)* | **bind an already-reserved id the predecessor already points at** | ~**1×** (one new blob; nothing rewritten) | one i-node per entry, no patch |

## 3. Design

### 3.1 Objects and the handle

```
root  { magic 'CLOG', version, flags, capacity_bytes,     -- 1 i-node, rewritten only
        waypoint_id, head_id(hint), live_bytes(hint) }        at checkpoints (~1/K appends)
entry { next_id, len, bytes… }                            -- 1 i-node PER log record

logring_t (RAM handle, rebuilt at open):
      { root, tail_id, next_free, live_bytes, appends_since_ckpt }
```

- `bytes` is caller-opaque (R8); `len` is `uint16` — an entry fits one
  `blob_db` payload (**no record spanning**, `-EMSGSIZE` above it).
- `next_id` points at a **reserved-but-unbound** id — the slot the *next*
  append binds.
- The root holds **no exact tail**: it carries a **waypoint** (a live entry
  *near* the end), plus `head_id`/`live_bytes` hints. It is rewritten only at
  checkpoints, so the single root i-node is no longer a per-append hotspot.
- The **handle** caches the exact `tail_id`/`next_free` in RAM. It holds no
  record data — only pointers — and is rebuilt by one bounded walk at `open`
  (§3.5). Per `l2_containers.md` §2.3, an L2 container handle is expected to
  hold "the root id plus O(1) cursor state"; this is that.

### 3.2 The pre-reservation invariant

> `tail.next_id` is always an id returned by `alloc_id()` that **no slot has
> been bound to yet**. The chain *ends* at the first `next_id` that
> `blob_db_get` reports `-ENOENT` because it is **unbound**.

`blob_db` keeps an allocated id durable and never re-issues it (as `rootreg`
relies on), so a reservation survives crashes at zero flash cost.

### 3.3 `append` — one write, warm O(1)

```
R  = h.next_free                         // cached; old_tail.next_id already == R
R2 = alloc_id()                          // reserve the next slot (durable, 0 flash)
write entry[R] = { next_id = R2, bytes } ◄── COMMIT: binding R makes it reachable
h.tail_id = R;  h.next_free = R2;  h.live_bytes += len;  h.appends_since_ckpt++
if h.appends_since_ckpt ≥ K  OR  h.live_bytes > capacity_bytes + slack:
        checkpoint_and_maybe_evict(h)    // §3.4 — the only root write
```

Binding `R` is the commit (the predecessor already points at `R`); the
predecessor is never touched. Warm cost = **one entry write, zero reads**,
~1× amplification. No root write except at a checkpoint.

### 3.4 Checkpoint + (batched) eviction — the only root write, the only intent

A steady-state full ring would evict on every append; to keep that from
restoring a per-append root write, eviction is **batched** and **ridden on the
checkpoint** (R4's soft budget allows an overshoot of ~`slack`):

```
checkpoint_and_maybe_evict(h):
  if over budget: walk head → new_head freeing ≥ (live_bytes − capacity_bytes)
      STAGE intent { del = head_id, del_next = head.next_id, stop = new_head_id }
      COMMIT root { waypoint = h.tail_id, head_id = new_head_id, live_bytes }  ◄ single root write
      CLEANUP  while del != stop: blob_db_delete(del); advance via del_next (resumable)
               CLEAR intent
  else: write root { waypoint = h.tail_id, head_id, live_bytes }               // plain checkpoint
  h.appends_since_ckpt = 0
```

So the root is written **~once per K appends**, and that one write does double
duty: refresh the **waypoint** (for `open`/`seek_newest`) *and* advance
**head** (eviction). Entry deletes are by id, spread across buckets — no
hotspot. The run intent carries each step's **successor** (`del_next`), not an
id range: evicted entries form a chain segment whose id *values* are not
contiguous (other logs/users interleave allocations, R9), so recovery must
follow the chain, never "delete every id in a range." A hard `-ENOSPC` on a
bind forces an immediate eviction regardless of the soft trigger.

### 3.5 `open` / recovery

`open(root, h)` reads the root and rebuilds the handle:

- **Rebuild the tail.** Walk from `waypoint_id` via `next_id` to the first
  unbound id — the last bound entry is `tail_id`, the unbound id is
  `next_free`. Bounded by appends since the last checkpoint (< K).
- **Finish any eviction.** If an intent is present, roll forward
  (`root.head_id == intent.stop`) by resuming its resumable delete loop, or
  roll back (clear it, delete nothing) otherwise. Idempotent.
- Hints (`head_id`, `live_bytes`) are adopted as-is; they are approximate and
  never a correctness input.

The chain always ends at a reserved-unbound id, so the true end is found
regardless of crashes; nothing extra is persisted. (Waypoint-evicted is an
edge case — only if the live set shrank below one checkpoint interval — handled
by falling back to a walk from `head_id` and re-checkpointing.)

### 3.6 Reading — an opaque, persistable cursor

Modeled on the systemd-journal / `lseek` idiom: an opaque position, seek to the
ends, step forward.

```
logring_cursor  — opaque position token; copy it to persist, pass back to resume
seek_oldest(c)              → c positioned at the oldest entry          (≈ seek_head)
seek_newest(h, c)           → c positioned at the newest entry, O(1)    (≈ seek_tail / SEEK_END)
next(h, c, out…)            → deliver the entry at c, advance c         (≈ sd_journal_next)
```

`next` delivers the entry **at** the cursor and advances to its `next_id`.
Detection:

- cursor position `< head_id`, or the entry reads `-ENOENT` while it should be
  live → **`-ESTALE`** (evicted by retention; cursor resets to oldest). R7.
- the entry's successor is the unbound frontier → **`-ENOENT`** caught up.

`seek_newest` is O(1) — the handle already holds `tail_id` (G1). Resume (R6) is
one read of the cursor's entry. The cursor is plain data: persist it (e.g. a
`rootreg` entry) and continue across reboot.

## 4. Cost summary (4 KB sectors; `N` buckets ≈ 2045 on 8 MB native_sim)

| Op | Flash reads | Flash writes | Caller RAM |
|---|---|---|---|
| `create` | 0 | 1 (root) | O(1) |
| `open` | 1 (root) + walk (< K) | 0 | O(1) |
| `append` (warm, no checkpoint) | 0 | 1 (entry) | len |
| `append` (checkpoint, maybe evicting M) | 0 (+ walk M if evicting) | 1 entry + 1 root + M deletes (+intent) | len |
| `next` (steady) | 1–2 | 0 | entry len |
| `seek_newest` + `next` | 1 | 0 | entry len |
| `stats` | 0 (from handle) | 0 | O(1) |

Every row is **O(1) in the log's total size** and amplification is ~1×
regardless of size, so the design carries no capacity ceiling (R1). Two
top-end constraints remain *allocator interactions*, not structural limits:
**compaction headroom** (size `capacity_bytes` below the raw partition; the
`-ENOSPC` backstop is the correctness floor) and, now much reduced, root-bucket
wear (~1/K of appends). A 1.5 MB / ~200 B-entry log ≈ 7 800 entries ≈
~1.5 MB of entry writes + ~`7800/K` small root writes — versus ~48 MB for
packed segments.

## 5. Public API (`include/app/lib/containers/logring.h`)

```c
typedef struct logring logring_t;        /* opaque RAM handle (root + cached tail) */
struct logring_cursor { /* opaque */ };  /* position token; copy to persist/resume */
struct logring_cfg   { uint32_t capacity_bytes; };            /* soft retention bound */
struct logring_stats { uint64_t oldest_id, newest_id; uint32_t count, bytes; };

/* lifecycle */
int  logring_create (const struct logring_cfg *cfg, uint64_t *out_root);
int  logring_open   (uint64_t root, logring_t *h);
int  logring_destroy(logring_t *h);                           /* delete all entries + root */

/* write — one record, durable on return; -EMSGSIZE if len > one payload */
int  logring_append (logring_t *h, const void *rec, size_t len, uint64_t *out_id);

/* read — forward-only, opaque cursor */
void logring_seek_oldest(struct logring_cursor *c);
int  logring_seek_newest(logring_t *h, struct logring_cursor *c);           /* G1, O(1) */
int  logring_next   (logring_t *h, struct logring_cursor *c,
                     void *out, size_t out_sz, size_t *out_len, uint64_t *out_id);
     /* 0 delivered · -ENOENT caught up · -ESTALE position evicted · -EMSGSIZE buf too small */

/* introspection / maintenance */
int  logring_stats  (logring_t *h, struct logring_stats *out);  /* ids exact; count/bytes hints */
int  logring_reset  (logring_t *h);
```

`logring` keeps its **own append/scan API** — a self-evicting, cursor-drained
log is neither a `map_ops` nor a `seq_ops` shape, and `l2_containers.md` §3
allows a container with its own op surface. Each `create` yields an independent
root/handle (R9); roots are persisted as the caller persists any structure root
(typically a `rootreg` entry per log, `ROOTREG_KEY('CLOG', n)`).

## 6. Crash analysis (the P7 check)

**Append** — no intent; the only commit is binding the pre-reserved entry
(atomic `blob_db_update`). A crash leaves complete-old or complete-new; a
reserved-unbound id costs zero flash; the RAM handle is rebuilt at `open`.

**Checkpoint/eviction** — the single `root` write (waypoint + head) is the
commit; the resumable run intent `{del, del_next, stop}` reclaims evicted
entries by following the chain. Recovery rolls forward (`head_id == stop`) or
back (clear intent), both idempotent, no leak, no dangling.

## 7. Container-invariant checklist (`l2_containers.md` §5)

1. **Single-integer reachability** — the root id recovers the whole log (the
   handle is a rebuildable cache). ✓
2. **Typed root** — `'CLOG'` magic/version; wrong-type `open` → `-ENOTSUP`. ✓
3. **One commit point per mutation** — append = bind entry; eviction/checkpoint
   = the root write. ✓
4. **O(1) steady-state RAM** — the handle is a few integers; no per-entry RAM. ✓
5. **Bounded stack** — one payload buffer; the open walk is iterative, ≤ K. ✓

## 8. Kconfig

```
config BLOB_CONTAINER_LOGRING
	bool "logring — bounded per-entry log container"
	select BLOB_CONTAINERS_INTENT        # eviction's resumable run intent (§3.4)

config BLOB_CONTAINER_LOGRING_CHECKPOINT   # K — appends between root checkpoints
	int  "logring checkpoint interval"
	default 32
```

`capacity_bytes` stays a per-log create-time parameter (soft hint). `K` trades
open-walk length and eviction-overshoot (~K entries) against root-write
frequency (~1/K); default 32.

## 10. Test plan (`tests/lib/containers/logring`, native_sim)

1. create → open → empty; `seek_oldest`/`seek_newest` + `next` → `-ENOENT`.
2. append/drain: ids strictly increasing; `next` oldest→newest; binary &
   zero-length records; `seek_newest` delivers the newest.
3. pre-reservation: `tail.next_id` is unbound; the next append binds exactly it.
4. **amplification guard**: count bytes via the flash shim — per-append ≈ entry
   size, root writes ≈ appends/K.
5. soft ring: append past `capacity_bytes`; eviction batches; `stats.bytes`
   settles within ~slack of the budget; fill the partition → `-ENOSPC` backstop
   evicts and the append still succeeds.
6. cursor resume: persist a cursor, unmount/mount (`open` rebuilds the handle),
   `next` continues; O(1).
7. **eviction detection**: hold a cursor, evict past it, `next` → `-ESTALE`.
8. **checkpoint/open**: crash with < K un-checkpointed appends; `open`'s walk
   from the waypoint recovers the exact tail; `next_free` correct.
9. **crash injection** (via `blob_db_test_cut`) at each step of §3.3/§3.4:
   remount, assert complete-old/complete-new, no unreferenced entry, intent
   cleared.
10. `destroy` removes all entries + root; `blob_db_count` returns to baseline.

## 11. Resolved decisions

- **D1 — capacity.** `capacity_bytes` per-log, **soft hint** (`live_bytes` in
  the handle, checkpointed into the root; `-ENOSPC` hard backstop). No
  crash-exact accumulator. ✓
- **D2 — root-write wear.** Resolved by the **waypoint + RAM-cached tail +
  checkpoint every K**: warm appends do no root write; the root (hence its
  bucket) is written ~1/K of appends. ✓
- **D3 — gap count on `-ESTALE`.** Detection only; **no per-entry seq** (ids
  are monotonic but not dense). ✓
- **D4 — per-entry magic.** None; rely on `blob_db`'s per-slot CRC. Entry
  overhead is `next_id` + `len`. ✓
- **D5 — intent dependency.** `select BLOB_CONTAINERS_INTENT`. ✓
- **G1 read-the-end.** `seek_newest` (O(1) via cached tail); forward-only, so
  "position at the end / follow", not backward "last N". ✓

Remaining tunable, not blocking: **K** (default 32).

## 12. Summary

A large, individually-addressable log (up to near the whole partition, R1) is
served by a forward chain of per-entry i-nodes with **pre-reserved** links:
each append binds a durable, already-pointed-at id, writing one blob and
rewriting nothing (~1×). A **RAM handle** caches the tail so warm appends are
O(1) and the root is written only at **checkpoints** (~1/K appends), which
also carry the **waypoint** (`open`/`seek_newest` anchor) and batch
**eviction** — dissolving the per-append root-write hotspot. Reads use an
**opaque, persistable cursor** (journal-/`lseek`-style) with O(1) resume and
`-ESTALE` on an aged-out position, and `seek_newest` reaches the real end in
O(1) (G1). Append is intent-free; only eviction carries a small resumable run
intent. The design upholds every §5 invariant and every P7 crash obligation.
