# Design change proposal — `logring`, a log container of per-entry i-nodes

Status: **proposal / for review** · 2026-10-08
· Target contract: `doc/layers/l2_containers.md` (§3 shapes, §4 containers, §5 invariants)
· Target implementation design: **replaces** `doc/impl/l2_logring.md` (today's single-i-node sketch)
· Depends on: `lib/containers/intent` (scaffolded) — **eviction only**
· Supersedes: the single-i-node `logring` currently on branch `claude/log-container-type-0xl2dp` (PR #32), not yet on `main`
· Governed by `doc/principles.md`

**The ask.** Store a device log of **1–2 MB** — many entries, **each its own
i-node** — as a bounded ring: appends cheap and kind to NOR, a forward drain
with a **persistable cursor** that resumes in O(1) and **detects when its
position has aged out** under retention.

**Short answer.** A **forward-linked chain of per-entry i-nodes with
pre-reserved ids**. Each entry's `next_id` points at an id that is already
reserved (`alloc_id`) but not yet bound; the next append simply *binds* that
id. So **append writes exactly one new blob and never rewrites an existing
one** — ~1× write amplification, independent of entry size, versus 2× for a
patch-the-predecessor chain and up to 32× for packed segments (§2). The
entry's own `blob_db` id is the cursor moniker; an aged-out position is
detected for free from the tombstone-no-reuse guarantee and the
ids-increase-head→tail invariant (§3.6). **Append needs no intent blob; only
eviction needs a one-id intent** (§3.4).

---

## 1. Requirements (settled in design discussion)

| # | Requirement | Consequence |
|---|---|---|
| R1 | A log holds **1–2 MB** | cannot live in one i-node; must be a chain of i-nodes |
| R2 | **Each entry is its own i-node** (its own stable id) | entry is individually addressable and individually evictable; its id can serve as the cursor |
| R3 | **Per-record durability, no RAM buffering** — written straight to `blob_db` | stateless, handle-free (root id is the whole handle); every append is a flash commit |
| R4 | **Approximately** bounded ring, evict oldest over a **soft** budget | strict item/byte limiting is *not* required — the budget is a hint, so no crash-exact accumulator is maintained |
| R5 | **Forward-only** reads | a singly-linked forward chain suffices |
| R6 | **Fast resume from a stored moniker** (O(1), not a scan) | the moniker locates its entry in one read |
| R7 | **Detect a moniker whose position was evicted** | retention gap is a first-class, reported outcome |
| R8 | Records are **caller-opaque bytes** | the container frames only a length |

R3 is the one that kills a buffering scheme and forces the amplification
question below to the front.

## 2. Why the obvious designs are too expensive

`blob_db` has **no append-to-blob primitive**: `blob_db_update(id, …)`
replaces the whole payload. Every "add one record" therefore costs a whole
blob write somewhere. The question is *whose*.

| Design | How a record is added | Flash written per record | Note |
|---|---|---|---|
| **Packed segments** (records packed N-per-i-node) | rewrite the open segment blob | `S²/2R` to fill an `S`-byte segment with `R`-byte records → ~**32×** at `S`=4 KB, `R`=64 B | the structure we started from; amplification explodes for small records |
| **Chain, patch predecessor** (entry holds `next_id`, set on the *next* append) | write new entry + **rewrite old tail** to set its `next_id` | ~**2×** (old tail's whole payload rewritten just to flip 8 bytes) | constant, size-independent, but still doubles wear |
| **Chain, two i-nodes** (immutable payload node + tiny mutable `link` node) | write payload + write link + patch previous link | ~**1× payload** + two tiny link writes | ~1× but **two i-nodes per entry** and an extra write |
| **Chain, pre-reserved id** *(recommended)* | **bind an already-reserved id the predecessor already points at** | ~**1×** (one new blob, nothing rewritten) + a small fixed root update | one i-node per entry, no patch, no extra node |

The recommended design gets the two-node design's ~1× *and* keeps one i-node
per entry, by moving the link into the future instead of into a side node.

## 3. Design — pre-reserved forward chain

### 3.1 Objects

```
root  { magic 'CLOG', version, flags, capacity_bytes,            -- 1 i-node, small,
        live_bytes(hint), head_id, tail_id, next_free }             rewritten per append
entry { next_id, len, bytes… }                                   -- 1 i-node PER log record
```

- `bytes` is caller-opaque (R8); `len` is a `uint16` (an entry fits one
  `blob_db` payload — **no record spanning**, `-EMSGSIZE` above it).
- `next_id` points at a **reserved-but-unbound** id — the slot the *next*
  append will bind.
- The root is a hint/accounting node (endpoints, the next reservation, and the
  soft byte budget); it is rewritten each append but it is ~40 B, and its
  structural fields (`head_id`/`tail_id`/`next_free`) are recoverable by a
  chain walk if stale (§3.5).
- `live_bytes` is a **non-authoritative hint** (R4): it rides the root write
  every append/eviction already does, so it costs **zero extra writes**, and it
  is never relied on for correctness — only to decide when to trim. It may
  drift by an entry across a crash; nothing reconciles it (§3.5). A `count` is
  not stored — when wanted it is approximated by `tail_id − head_id` (ids
  increase head→tail, §3.6), no separate counter.

### 3.2 The pre-reservation invariant

> `tail.next_id` is always an id returned by `alloc_id()` that **no slot has
> been bound to yet**. The log "ends" at the first `next_id` in the chain that
> `blob_db_get` reports `-ENOENT` *because it is unbound*.

`blob_db` guarantees an allocated id is **durable and never re-issued** even
while unbound (the same property `rootreg` relies on), so a reservation
survives crashes and reboots at zero flash cost.

### 3.3 `append(bytes)` — one write, nothing rewritten

```
R  = root.next_free                 // already == old_tail.next_id
R2 = alloc_id()                     // reserve the slot AFTER this one (durable, 0 flash)
write entry[R] = { next_id = R2, bytes }        ◄── COMMIT (single blob_db_update)
update root { tail_id=R, head_id (if first), live_bytes += len (hint), next_free=R2 }
evict from head while live_bytes(hint) > capacity_bytes             // §3.4, soft
```

**Binding `R` is the commit**: before it, a reader walking `… → old_tail →
R` finds `R` unbound and stops (log = old); after it, `R` is a live entry
(log = new). The flip is one atomic `blob_db_update`, and it writes the
*new* entry — the predecessor is never touched. First-ever append has no
predecessor, so its commit is the root update that sets `head_id = R`
(a single-node case).

Write cost per append = **one entry (written once, forever) + one ~40 B root
update**. Amplification ≈ **1×** + a fixed sliver, independent of entry size.

### 3.4 Eviction — the only place an intent is needed

Trim the oldest when the **soft** `live_bytes` hint exceeds `capacity_bytes`,
and **unconditionally** when an append's bind returns `-ENOSPC` — the hard
backstop that keeps a full partition from wedging the log (bind → on `-ENOSPC`,
evict head, retry). Because the trigger is a hint, the ring is approximate by
design (R4): it may sit a little over or under budget, never exactly on it.

```
STAGE    intent { evict = head_id }           // one id
advance  root.head_id = head.next_id          // head no longer reachable  ◄ commit
delete   blob_db_delete(old_head)             // reclaim its flash
         live_bytes -= old_head.len (hint)
CLEAR    intent
```

`head.next_id` is known (it is in the head entry), so eviction is O(1) and
forward. A crash **between** advancing `head_id` and the delete leaves
`old_head` as an *unreferenced bound blob*. Two independent facts reclaim it,
so recovery is trivial:

- the one-id **intent** names it explicitly, and
- the **ids-increase-head→tail invariant** (§3.6) means *any bound id below
  `head_id` is evictable residue* — a belt-and-suspenders check that needs no
  intent at all.

(The add path in §3.3 needs **no** intent: its only possible residue is a
reserved-unbound id, which costs zero flash and is reclaimed by nothing being
needed.)

### 3.5 `open` / recovery

`open(root)` reads the root, validates `'CLOG'` + version — no scan. Recovery
is driven entirely by the two cheap invariants:

- **Stale root self-heals.** If a crash hit §3.3 after the commit but before
  the root update, `root.tail_id`/`next_free` are one behind. Walk from
  `tail_id` following `next_id` to the first unbound id; the last bound entry
  is the true tail, the unbound id the true `next_free`. Bounded by appends
  since the last root write (≈ 1).
- **Eviction residue** is finished from the intent (or, failing that, by
  reclaiming bound ids `< head_id`).
- **The `live_bytes` hint is not reconciled.** A crash between the §3.3 commit
  and the root update, or inside §3.4, may leave it off by an entry. That only
  shifts the next eviction point by one entry and is never a correctness
  input, so recovery ignores it (the `-ENOSPC` backstop covers the extreme).

The first two are idempotent and bounded — P7's "no permanent leak" with no
new machinery.

### 3.6 The cursor / moniker contract

```
struct logring_cursor { uint64_t last_id; };   // last delivered entry id; 0 = before head
```

The moniker is **one `uint64_t`** — the id of the last entry the consumer
read — persistable verbatim (e.g. in a `rootreg` entry) and reboot-stable.

`logring_next(root, &c, out…)`:

1. read root (`head_id`, …).
2. `c.last_id == 0` → candidate = `head_id`.
3. else if `c.last_id < head_id` → **`-ESTALE`**: the position was evicted;
   set `c.last_id = 0` so a retry resumes at the oldest survivor (R7).
4. else read `entry[last_id]`, candidate = its `next_id`.
5. candidate unbound (`get` → `-ENOENT`, candidate ≥ `head_id`) → `-ENOENT`
   *caught up* — nothing new yet.
6. else deliver `entry[candidate]` (id + bytes), set `c.last_id = candidate`.

**R6 (fast resume):** one read of the stored entry gives `next_id` — O(1), no
scan. **R7 (eviction detection):** the ids-increase invariant makes
`last_id < head_id` an exact, O(1) test, and `blob_db`'s tombstone (`get` →
`-ENOENT` for a deleted id) is an independent confirmation. **Caught-up vs.
evicted** is thus unambiguous: below `head_id` = evicted, at-or-above with an
unbound `next` = caught up.

*Note (for review, §11-D3):* because ids are monotonic but **not dense**,
`-ESTALE` reports *that* a gap exists but not *how many* records were lost. A
dense count would need an extra per-entry sequence number; the requirements
asked for detection, not an exact tally.

## 4. Cost summary (4 KB sectors; `N` buckets ≈ 2045 on 8 MB native_sim)

| Op | Flash reads | Flash writes | Caller RAM |
|---|---|---|---|
| `create` | 0 | 1 (root) | O(1) |
| `append` (no eviction) | 1 (root)¹ | 1 entry + 1 root | len |
| `append` (one eviction) | + 1 (head) | + 1 intent + 1 delete + 1 intent-clear | len |
| `next` (steady) | 2 (root + entry) | 0 | entry len |
| `seek_resume` + first `next` | 2 | 0 | entry len |
| `stats` | 1 (root) | 0 | O(1) |
| `open` (clean) | 1 (root) | 0 | O(1) |
| `open` (after crash) | 1 + walk (≈1) | ≤ intent cleanup | O(1) |

¹ plus the one-time cold-bucket erase `blob_db` already amortizes via
`blob_db_prepare()`. A 1.5 MB log at ~200 B/entry ≈ 7 800 entries ≈ 7 800
entry writes + 7 800 small root writes ≈ **~1.5 MB + ~0.3 MB** of flash —
versus ~48 MB for the packed-segment design at the same entry size.

## 5. Public API (`include/app/lib/containers/logring.h`)

```c
struct logring_cfg { uint32_t capacity_bytes; };   /* retention bound (§11-D1) */

int logring_create (const struct logring_cfg *cfg, uint64_t *out_root);
int logring_open   (uint64_t root);                 /* validate magic/type */
int logring_destroy(uint64_t root);                 /* delete every entry + root */

int logring_append (uint64_t root, const void *rec, size_t len,
                    uint64_t *out_id);              /* -EMSGSIZE if len > one payload */

struct logring_cursor { uint64_t last_id; };        /* the moniker — persist verbatim */
void logring_seek_oldest(struct logring_cursor *c);         /* last_id = 0 */
int  logring_next(uint64_t root, struct logring_cursor *c,
                  void *out, size_t out_sz, size_t *out_len, uint64_t *out_id);
     /* 0 delivered · -ENOENT caught up · -ESTALE position evicted (c reset to head)
      * -EMSGSIZE out_sz too small (cursor not advanced) */

struct logring_stats {
    uint64_t oldest_id, newest_id;   /* exact (head_id / tail_id) */
    uint32_t count, bytes;           /* hints — bytes is live_bytes, count ≈ id span */
};
int logring_stats(uint64_t root, struct logring_stats *out);
int logring_reset(uint64_t root);                   /* drop all entries */
```

`logring` keeps its **own append/scan API** (it is not a `map_ops`/`seq_ops`
provider): a self-evicting, cursor-drained log is neither shape, and forcing
it into `seq_ops` would mislead (`get(index)` is not meaningful once the head
slides). `doc/layers/l2_containers.md` §3 already allows a container with its
own op surface.

## 6. Crash analysis (per crash point, the P7 check)

**Append** (no intent; residue is at worst a free reservation):

| Crash point | On flash | Visible state | Residue |
|---|---|---|---|
| after `alloc_id` (R2) | nothing new | old log | R2 unbound — 0 flash, reclaimed by disuse |
| after COMMIT (bind R) | entry R live, reachable via old_tail.next_id | **new** log | root stale → self-heals (§3.5) |
| after root update | entry R live, root current | new log | none |

**Eviction** (one-id intent):

| Crash point | On flash | Visible state | Residue |
|---|---|---|---|
| after STAGE | head still reachable | unchanged | intent set → re-run, idempotent |
| after advance `head_id` | old_head unreferenced | head trimmed | old_head leaked → reclaimed from intent (or id `< head_id`) |
| after delete | old_head gone | head trimmed | intent set → CLEAR on next open |

No crash yields a dangling reference or a partially-written entry (each entry
is one atomic `blob_db_update`), nor a permanent leak.

## 7. Container-invariant checklist (`l2_containers.md` §5)

1. **Single-integer reachability** — root id recovers the whole log; the
   cursor is itself one id. ✓
2. **Typed root** — `'CLOG'` magic/version; wrong-type `open` → `-ENOTSUP`. ✓
3. **One commit point per mutation** — append = binding R; eviction = advancing
   `head_id`. ✓
4. **O(1) steady-state RAM** — stateless; no per-entry RAM, no cache. ✓
5. **Bounded stack** — one payload buffer (≤ `BLOB_DB_MAX_PAYLOAD_LEN`); no
   recursion. ✓

## 8. Kconfig

```
config BLOB_CONTAINER_LOGRING
	bool "logring — bounded per-entry log container"
	select BLOB_CONTAINERS_INTENT        # eviction's one-id intent (§3.4)
```

`capacity_bytes` is a **per-log create-time parameter** (§11-D1), not a
Kconfig — different logs want different budgets and it costs one root field.
The intent helper (`lib/containers/intent`, scaffolded today) must be
implemented for the eviction path; this proposal is its first consumer and its
usage is deliberately minimal (a single id), which is a useful first exercise
of that module.

## 10. Test plan (`tests/lib/containers/logring`, native_sim)

1. create → open → empty (`stats` zero, `next` → `-ENOENT`).
2. append/drain round-trip: ids strictly increasing; `next` delivers
   oldest→newest; binary and zero-length records.
3. pre-reservation: after append, `tail.next_id` is unbound (`get` →
   `-ENOENT`); the following append binds exactly that id.
4. **amplification guard**: instrument the flash shim to count bytes written;
   assert per-append writes ≈ entry size + root, *not* O(segment).
5. soft ring: append well past `capacity_bytes`; oldest entries evicted;
   `stats.bytes` settles **within about one entry of** `capacity_bytes` (hint,
   not strict); `oldest_id` advances. Separately: fill the partition and assert
   the `-ENOSPC` backstop evicts and lets the append succeed.
6. cursor resume: persist `last_id`, unmount/mount, `logring_next` continues;
   O(1) (one entry read) — asserted via the read counter.
7. **eviction detection**: hold a `last_id`, evict past it, `logring_next` →
   `-ESTALE` and resets to head.
8. persistence across unmount/mount (single-integer recovery).
9. **crash injection** at every step of §3.3 and §3.4 (reuse the
   `blob_db_test_cut` harness): remount, assert visible state is complete-old
   or complete-new and no unreferenced entry survives (P7), intent cleared.
10. `destroy` removes every entry + root; `blob_db_count` returns to baseline.

## 11. Decisions needed from review

- **D1 — capacity unit & strictness.** `capacity_bytes` per-log at `create`,
  enforced as a **soft hint** (R4): `live_bytes` rides the existing root write
  (zero extra writes), is not crash-reconciled, and `-ENOSPC` is the hard
  backstop. Strict byte/item limiting is *not* required and is deliberately not
  provided (it would need a crash-exact accumulator). Alternative units: a
  max-entry **count** (same hint mechanics via `tail_id − head_id`) or a global
  Kconfig. Recommendation: **soft `capacity_bytes`**.
- **D2 — root write per append.** Keep the root current every append (O(1)
  open, ~0.3 MB of root writes over a 1.5 MB log) vs. update it lazily and
  lengthen the §3.5 heal walk. Recommendation: **keep current** — the root
  write is tiny and O(1) open is worth it.
- **D3 — exact gap count on `-ESTALE`.** Accept "a gap exists" (ids are not
  dense), or add a per-entry `uint64 seq` for an exact lost-count? The
  requirements asked for *detection*; recommendation: **no seq** unless a
  consumer needs the tally.
- **D4 — per-entry magic.** Add a 2-byte tag to `entry` for corruption
  detection (entries are only reached via a typed root, so it is optional) or
  rely on `blob_db`'s per-slot CRC? Recommendation: **rely on the slot CRC**;
  keep entry overhead at `next_id` + `len`.
- **D5 — `select` vs `depends on` for the intent helper.** `select
  BLOB_CONTAINERS_INTENT` (recommended, auto-resolves the slice like
  `kvhash` selects `kvlist` historically) vs. a `depends on` the user must
  satisfy.

## 12. Summary

A 1–2 MB log of individually-addressable entries is best served not by packing
(32× wear) nor by patching predecessors (2× wear), but by **pre-reserving the
next id**: each append binds a durable, already-allocated id that the previous
entry already points at, so it writes one new blob and rewrites nothing (~1×).
The entry's own `blob_db` id is the persistable cursor moniker, and the
ids-increase-head→tail invariant plus `blob_db`'s tombstone-no-reuse turn
"did my position age out?" into an O(1), unambiguous answer. Append is
intent-free; only eviction carries a one-id intent, making `logring` a minimal
first consumer of the shared intent helper. The design upholds every §5
container invariant and every P7 crash obligation with two small, idempotent
recovery rules.
